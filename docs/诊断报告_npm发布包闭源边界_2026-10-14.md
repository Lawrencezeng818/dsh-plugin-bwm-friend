## 三、可行方案（唯一同时满足两目标的路径）

### 3.1 方案 R · 运行时外部加载（**推荐**）

**原理**：壳在运行时 `require` 一个**独立分发的闭源运行时包**，而不是把它内联进 bundle。

```
路A（现状 · 不可接受）
  构建期：读内核源码 → 内联进 client.js → 全明文随包出网

路 R（推荐）
  构建期：client.js 只留 require('@laikaton/bwm-runtime')  ← 不内联
  运行期：宿主从私有分发渠道加载闭源运行时（独立包 / 私有 registry）
```

**为什么这是唯一解**：壳必须 `require` 内核（这是既定架构），而 `require` 到哪里由**部署侧**决定，**不取决于打包**。因此源码不必进 npm 包。

### 3.2 必须同步处理的连带项（**不可遗漏，否则功能会坏**）

| # | 连带项 | 原因 |
|---|---|---|
| 1 | `tests/build-artifact-parity.mjs` | 校验侧同样注册 `INLINE_MODULES`，**两侧必须同改**，否则假 FAIL（`inline-modules.mjs` 注释记载过这个坑） |
| 2 | `scripts/audit-release.mjs` 的 `CORE_FINGERPRINTS` | 改路径后指纹定位失效，**须重指**，否则门禁误报 |
| 3 | **`package.json` `test:core`** | 现为 `cd packages/bwm-runtime-core && node --test test/*.test.js`——内核移出仓内后**此脚本失效**，须改为对运行时包测试 |
| 4 | 离线/内网用户 | 私有 registry 不可达时需明确降级路径（**不得静默失败**） |
| 5 | 授权校验（**待你裁定**） | 闭源包的分发是否绑定 license key，属商业设计，见 §五待决项 |

### 3.3 明确否决的替代路径

| 路径 | 否决理由 |
|---|---|
| 混淆/压缩后随包 | 提高阅读门槛，**不构成闭源**；npm 用户可直接 `npm view` 解包 |
| 裁剪 `lib` 只留壳 | 壳 `require` 内核失败 ⇒ **装完跑不起来**，与你裁定的(a) 直接冲突 |
| 接受核心开源换铺量 | 你已明确否决 |
