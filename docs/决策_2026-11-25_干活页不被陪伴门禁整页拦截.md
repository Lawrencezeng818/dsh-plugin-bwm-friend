# 决策：干活页（`/bwm-friend/work/`）不被陪伴门禁整页拦截

- 日期：2026-11-25
- 版本：0.8.51
- 状态：已实施
- 触发：为拍市场截图启动真实宿主，发现干活页被全屏遮罩盖死

## 结论

`companion-chat.js` 的 `initGate()` 增加分流：`body[data-bwm-mode="work"]` 时**提前返回**，
不在进页时铺全屏登录遮罩。陪伴页（`/bwm-friend/companion/`）行为不变。

## 依据（三条，都可回查）

1. **门禁自己的文案就限定在陪伴模式**。`showGate()` 渲染的副标题是
   「陪伴模式需要登录后使用」，不是「BWM Friend 需要登录」。文案是产品意图的直接表述，
   比我的推断可靠。
2. **干活页另设独立账号入口**。设置面板里有「账号 / 会员」区（未登录态显示登录表单 +
   「没有账号？前往官网注册」），说明设计意图是**页可用、账号可选**。若整页本来就该被拦，
   这块 UI 是永远看不到的死代码。
3. **功能定位不同**。README 第 76 行：`/work/` 是「iframe 内嵌原生 DSH」的工作台，
   核心价值是干活；`/companion/` 才是需要身份的数字人陪伴。

## 未放松的部分

- 未登录点「发送」仍走 `showGate()`（`sendChat` 里的 `authRequired` 分支）。
- 服务端 `/bwm-friend/*` 的鉴权、`hostGate`、`isSameOriginRequest` 一个字节没动。
- 对照组实测：打桩 `auth/status → {loggedIn:false}` 后，`/work/` 无 gate，
  `/companion/` gate 仍在且 `pointerEvents:auto`。

## 反方意见（成立但未采纳）

「BWM 是会员产品，未登录就该什么都进不去」——若这是真实意图，则应当：①保留整页拦；
②把门禁文案从「陪伴模式」改成「BWM Friend」；③删掉干活页的未登录账号区。
三件事没做，说明现状是**文案与行为不一致**，改哪边都行，本轮选改动小的那边（改行为对齐文案）。

## 改判条件（满足任一即应翻案）

1. 运营要求「未登录不得进入工作台」（例如按席位/会员计费，或要采集登录漏斗）。
2. 干活页出现必须在登录后才安全的操作（当前没有：所有写操作仍走服务端鉴权）。
3. 市场/合规要求单一登录墙入口。

翻案时同步做上面反方那三件事，不要只改一处。
