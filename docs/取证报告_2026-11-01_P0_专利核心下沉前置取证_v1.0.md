## 二、Q2 取证：账本零写入，故无「写完即读」

### 2.1 命名撞车是误判源头（必须先纠正）

`src/client.js:1152`：

```js
const runtime = createRuntime({ ledger: createLedgerStore() });
```

这个 `ledger` 传进去后，在 `core/src/index.js:650` 被用作 **`wireLedger` 的 timeline store**（`opts.ledger ? { store: opts.ledger } : {}`），与关系账本**毫无关系**。
关系账本是 `core/src/index.js:653` 内部独立创建的：

```js
const relationshipLedger = createRelationshipLedger(opts.relationshipLedger || {});
```

即原方案 §2.2 表格写的「client（`src/client.js:1152`）→ 远程账本代理 `createRemoteLedgerStore()`」**改错了对象**——那一行是 timeline 存储，不是关系账本。

### 2.2 关系账本实例的全部使用点（全仓）

| 文件 | 行 | 用途 |
|---|---|---|
| `core/src/index.js` | 653 | 创建 |
| `core/src/index.js` | 662 | 挂到 `runtime.relationshipLedger` 导出 |

**再无第三处。** 全仓 `*.js/*.mjs/*.ts`（排除 node_modules 与构建产物）搜索 `relationshipLedger` 只有上述两行；`bwm-sdk`、`lib/index.js`、`invariant.js`、契约测试均未消费。

补充（2026-11-01 复核补记）：client 有**两处** `createRuntime()`（`:1115` 嵌入式握手不传 ledger、`:1152` 沉浸页传 timeline store），因此运行时实际会实例化**两个关系账本对象**——两个都没有任何输入，也都没有任何读取。这使"死代码"结论更强，而非更弱。

### 2.3 因此「写完即读」清单 = 空

| 可能的读点 | 实际情况 |
|---|---|
| 生产代码 `runtime.relationshipLedger.report()/replay()/verify()` | 0 处 |
| 生产代码 `ledger.submit()/write()` | 0 处（只有 8 个测试文件调用） |
| UI 读取 `context.timeline` | `src/client.js` 中 timeline 仅出现在注释与持久化段，**无渲染读取** |

Q2 关闭：**不是「异步化会引入时序风险」，而是「根本没有写入方，也就没有时序可破坏」**。
原方案风险 §5.1 的「最大技术风险」在当前代码状态下不发生。

### 2.4 但远程化会新造一个更硬的矛盾（原方案未识别）

`relationship-ledger.js` 的 `write()` 契约（`packages/bwm-runtime-core/src/relationship-ledger.js`，`先落持久层，成功后才更新内存权威视图` 段）：

```
store.append(entry) 同步成功 → 才 entries.push / seen.add → return { ok: true }
store.append 抛错        → return { ok:false, PERSIST_FAILED }，不提交
append 返回 rejected     → 异步回滚 entries（补丁式兜底）
```

而专利 4 第 6 步的技术效果正是「**原子幂等追加，持久化失败不提交**」。一旦 append 变成 HTTP：

- 同步契约必然破（网络无法同步）
- 只能「乐观提交 + 异步回滚」，回滚窗口内 `has(eventId)` 为真、`report()` 已计入
- 这与说明书里主张的技术效果**方向相反**

**结论：远程化不是重构，是把专利实施例与代码拉开距离。** 这是 R2 级风险，不是性能问题。

## 六、留给创世者的一个裁决（我不代填）

### D1｜审计的「内核」到底指什么

现状：审计把 **公开 runtime 面**（EventBus / Context / Presence / 人格常量）和 **专利实现**（专利 1/4/5）混在同一张红牌里。只要 client 还要用 runtime，红牌就永远挂着，`--expect-blocked` 只能永久常开——这与「冻结期临时模式」的设计意图已经背离。

三个口径，涉及专利公开边界（R2），必须你拍：

| 口径 | 内容 | 后果 |
|---|---|---|
| **A｜收窄** | 指纹与符号清单限定到真正的专利判定逻辑（4/5 + 专利1 六处），runtime 面定为公开 | 可解冻；需一次审计口径复核（建议过小沈） |
| **B｜维持** | 现口径不变 | 必须把 runtime 也移出 client —— 技术上不成立 → `--expect-blocked` 永久化 |
| **C｜分阶段** | 先收窄到「4/5 离包」可验证，专利 1 面单列为「待公开后解冻」 | 折中；审计有中间态 |

我倾向 **A**：审计的目标是「防专利自我公开」，不是「防自家 runtime 进包」；把公开面算进红牌，等于让红牌失去分辨力——而失去分辨力的门禁，最终会被绕过。

### 8.2 R3 指出的五处方案缺口（施工单必须覆盖）

1. `bridgePerceptionToLedger`（`core/src/index.js:603`）依赖 `UPDATE_MODES.PERSIST` 并调用 `ledger.submit()`，**只删两处 require 会留下语义残留** → 须一并迁移/删除/重构并改测试。
2. `runtime.relationshipLedger` 是**包公开契约**的一部分（`core/src/index.js:662`）→ 须定 minor/breaking 版本、CHANGELOG、core 测试与 parity 断言。
3. core 还引入/再导出 `RULE_TABLES`、`LEDGER_ERRORS`、`DOMAIN_CLASS`、`UPDATE_MODES`、`PERCEPTION_ERRORS` → 逐项说明新归属或删除。
4. 专利 1 残留（`RELATIONSHIP_POLICY`/`wireRelationship`/`RELATIONSHIP_SIGNALS`）**未在载荷内给源码段**，只能保留"待专利线复核"结论，**不得宣称"专利实现全部离包"**。
5. `npm pack` 白名单、parity 原文、`invoke` 契约未核验 → 验收须补 tarball 全量扫描 + `test:pack`/`test:fresh` 留痕。

3. 专利 1 残余风险与"待专利线复核"写入最终裁决记录。
4. `npm pack` 白名单、tarball 扫描、parity、`test:pack`、`test:fresh` 全量留痕。
5. 如仍需解除 F1–F6，另起独立裁决，先明确 runtime 公开面；不得借 P1-lite 一并放行。
6. `--expect-blocked` 如继续使用，必须带有效期与解冻依据，不得永久常开。
